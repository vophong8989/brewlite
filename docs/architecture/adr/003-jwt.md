# ADR-003: JWT và phân quyền

**Trạng thái:** Chấp nhận  
**Ngày:** 18/11/2026

## Bối cảnh
BrewLite có CUSTOMER, STAFF, MANAGER; SRS yêu cầu xác thực và phân quyền.

## Quyết định
Dùng `@nestjs/jwt` + Passport, bcrypt, JWT stateless payload `sub` và `role`; đăng ký công khai chỉ CUSTOMER, STAFF/MANAGER qua seed. Access token có thời hạn **1 giờ**, cấu hình `JWT_EXPIRES_IN=1h`; không triển khai refresh token trong MVP. Frontend lưu access token trong `localStorage` và gửi `Authorization: Bearer <token>` khi gọi API; token hết hạn hoặc response 401 thì xóa trạng thái đăng nhập và điều hướng về trang đăng nhập. API kiểm tra chữ ký, thời hạn và role, không tin role do client tự gửi.

## Hệ quả và trade-off
Ưu: REST stateless và guard đơn giản. Nhược: access token trong `localStorage` có thể bị lấy nếu website gặp XSS. Đây là rủi ro được chấp nhận trong phạm vi MVP, không phải bảo đảm an toàn tuyệt đối. Giảm thiểu bằng việc không render HTML thô từ người dùng, escape nội dung, kiểm soát script của bên thứ ba, Content Security Policy cơ bản và token sống ngắn; không log token hoặc secret. Khi triển khai cần kiểm chứng CSP không làm hỏng Next.js/PWA.

## Phương án đã cân nhắc
Session server-side: tăng trạng thái server và hạ tầng, không cần trong MVP. Cookie `HttpOnly`: giảm rủi ro lộ token qua JavaScript nhưng được loại trong phạm vi MVP vì web Vercel và API Render khác site/domain làm phức tạp CORS có credentials, SameSite và CSRF; đây là trade-off về phạm vi, không có nghĩa cookie `HttpOnly` không khả thi.
